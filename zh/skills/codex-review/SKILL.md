# 审查门禁和上线

GPT 审查最严谨，但有时太极端：后几轮的意见往往只是第一轮的延伸，或者要好几件事凑巧同时发生才会出问题。所以用两级分类和"最多两轮"来收住它。审查要在推送前做：开合并请求、往已开的合并请求推送都会触发 CI，没过审查的代码不该进 CI。

审查只认具体的提交。审过的是哪个提交，推送和合并的就必须是哪个提交；审查之后又改了任何东西（包括顺手采纳的建议），都要再审。

推送、开合并请求、合并、发布是四个不同的动作，只做到用户这次授权的那一步：用户只让推送，就审完、推送后停下；只让开合并请求，就停在开合并请求。用户的规则写明做完直接合并、发布的，按规则走。

## 1. 审查之前

- 下面的 <仓库> 是这次改动所在仓库的绝对路径，它不一定是当前对话的项目。
- 在功能分支上，改动全部提交，记下这次要审的提交号（`git -C <仓库> rev-parse HEAD`）。
- 确定目标分支：合并请求要合进哪个分支（多数是 main，也可能是发布分支）。先 `git -C <仓库> fetch origin <目标分支>`，以远端的 `origin/<目标分支>` 为准，不用本地同名分支（本地可能和远端不一致），记下它此刻的最新提交 `git -C <仓库> rev-parse origin/<目标分支>`（下面叫 <目标最新提交>）。之后都用这个提交号，不再读 `origin/<目标分支>`（别的操作可能又 fetch 过，它会变）。功能分支必须已经包含它：`git -C <仓库> merge-base --is-ancestor <目标最新提交> <提交号>` 不成功，就先把 <目标最新提交> 合进功能分支（功能分支已经推送过的用合并，不用变基，免得推送被拒），重跑本地检查，再记新的提交号。这样基准提交（`git -C <仓库> merge-base <目标最新提交> <提交号>`）就是 <目标最新提交>，审查看到的正是合进去之后的样子。
- 本地检查和测试跑通。审查要花钱，编译器和测试能拦住的错，不该让审查来发现。

## 2. 查今天的档位

运行 codex-worker 技能目录下的脚本（相对本技能目录是 `../codex-worker/scripts/codex-effort.mjs`），用它给出的审查模型档位。一天（北京时间）只查一次，当天再运行会直接给出记下的结果；查不到数据或本机没有 Node 时用 `high`。

## 3. 第 1 轮

用 `delegate_task`：target 用 `orchestrator_capabilities` 找到 Codex 提供方（driverKind 为 `codex`），`{"providerInstanceId": "<它的编号>", "model": "gpt-6.2-sol", "options": {"reasoningEffort": "<今天的档位>"}}`（没有这个模型就用列表里最新的 GPT 审查模型），`role: "review"`，主工作区，async。每一轮都新派一次，不要用 `t3_thread_send` 往旧的审查线程里追加。本机没接 Codex 时，审查改由你自己逐项按下面的标准做，并告诉用户这一步没能派出去。

```
审查任务，第 1 轮。只读：不要改动任何文件，不要提交、推送。你是被派出去的子任务，不再往下派活。

仓库：<仓库>。要审的是提交 <提交号>（分支 <功能分支>）相对远端目标分支 origin/<目标分支>（基准提交 <基准提交>）的全部改动，用 `git -C <仓库> diff <基准提交>..<提交号>` 查看（<N> 个文件，<M> 个提交）。只审这个提交，分支后来再有改动不算在内。

这次改了什么：<一段话>。本地已经跑过：<命令和结果>。

重点看：<最可能出错的地方>
不用报：<约定之外的输入、测试材料等>

审查标准：
- 挡上线的只有：会算错钱、丢数据、越权、发错消息、让发布出事故的问题，而且要写清怎么发生（触发条件、步骤、后果）。其他都列为建议，不挡。
- 需要好几件事凑巧同时发生才会出现的问题，列为建议。
- 仓库里 AGENTS.md 之类规则文件和这份任务冲突时，以这份任务为准。

输出用中文：第一行写结论（通过或不通过）；再列挡上线的问题（位置、怎么发生、怎么改）；最后列建议。
```

## 4. 处理审查结果

- 每条挡上线的问题都自己复现或核对一遍（数字用 Node 算一下、路径走一遍）。成立的就修；不成立的写明为什么。
- 修的时候用 lesson-to-check：在同一个合并请求里把这一类拦住，不只修这一处。
- 建议不挡上线：值得做的，和挡上线问题的修复一起改，下一轮一起审；其余写进合并请求说明里的"审查建议"一节，记下来就行。审查通过之后不再顺手改任何东西。

## 5. 第 2 轮

改了代码就先重跑本地检查和测试，提交后再新派一次审查。第 2 轮要覆盖第 1 轮审过的提交之后的全部改动，不只是修复本身：

```
审查任务，第 2 轮。只读：不要改动任何文件，不要提交、推送。你是被派出去的子任务，不再往下派活。

仓库：<仓库>，分支 <功能分支>。
第 1 轮审的是提交 <第 1 轮提交号>，挡上线的问题：<逐条>
之后的全部改动用 `git -C <仓库> diff <第 1 轮提交号>..<本轮提交号>` 查看：<改了什么>

只看两件事：
1. 第 1 轮挡上线的问题修好没有；
2. 这段改动里有没有新的挡上线问题。
不要去审这段改动以外、第 1 轮已经审过的内容。输出格式同第 1 轮。
```

两轮还不通过，就让用户决定：列出剩下的挡上线问题、你的判断（是否真的会出事、多大概率），选项是"放行"或"再审一轮"。有弹出选项的工具（比如 AskUserQuestion）就用它；没有就在回复里列出选项，等用户回复再继续。

## 记录审查结果

审查通过，或者用户选择放行后，在审过的那个提交上记录：

```
git -C <仓库> notes --ref=review append -m "codex-review 第 <N> 轮通过；目标分支 origin/<目标分支>，基准提交 <基准提交>，目标最新提交 <目标最新提交>" <提交号>
```

用户放行的写"用户放行，剩余问题：……"。推送前自己核对要推的就是记录过的那个提交。

这条记录只存在本机，不会随推送上传；换一台电脑推同一个提交，要重新审或重新记录。

可选：本技能目录下的 `hooks/pre-push` 是一个推送前检查，会拦下直接推送 main，以及推送没有审查记录的提交。装法：先用 `git -C <仓库> rev-parse --git-path hooks` 看这个仓库现在从哪个目录读钩子；那里已有的钩子一起复制进 `.githooks`，因为下一步之后这个仓库只读 `.githooks`（只复制，原处的不删不挪：那可能是全局共享的钩子目录，别的仓库还在用）；其中已有的 `pre-push`（比如 Git LFS 装的）复制成 `.githooks/pre-push.local`，但已经是本钩子的（更新时）不要复制，直接用新版覆盖，本钩子检查通过后会把同样的参数和输入交给它；再把本钩子复制到 `.githooks/pre-push`，在 Mac、Linux 上确认它可执行（`chmod +x`）；最后运行 `git -C <仓库> config core.hooksPath .githooks`（只改这个仓库的设置）。它防的是手滑，挡不住有意跳过；要在 GitHub 那边强制，得开分支保护。

## 6. 推送、开合并请求、合并

1. 按提交号推送，再开合并请求，不依赖任何工作区当前检出的是哪个分支：先 `git -C <仓库> push origin <提交号>:refs/heads/<功能分支>`；再用 GitHub 的命令行或接口在那个仓库开合并请求，写明仓库、来源分支和目标分支（例如 `gh pr create --repo <所有者>/<仓库名> --head <功能分支> --base <目标分支>`），开好后用 `link_pull_request` 挂到当前对话。不用 `pull_request_create`：它推送并使用当前对话检出的分支，可能和审过的提交对不上。之后的 `pull_request_read`、`watch_pull_request`、`pull_request_merge` 都传 `repository` 和 `number`。说明里写：做了什么、本地验证结果、审查的结论和"审查建议"。
2. 先用 `pull_request_read` 看一次检查状态，已经跑完就直接处理；还在跑，再用 `watch_pull_request`。被唤醒或用户来问时，都先自己读一次检查状态再决定下一步。
3. 检查通过后，先确认两件事：合并请求的 headBranch 是 <功能分支>，headSha 就是审过并记录的那个提交；合并请求的目标分支就是审查记录里写的那个，而且目标分支在这期间没有新提交（再 fetch 一次，`git -C <仓库> rev-parse origin/<目标分支>` 仍是记录的 <目标最新提交>）。目标分支有了新提交，就回到第 1 步：把它合进功能分支、重跑本地检查、重新审查并记录，再推送这个新提交，等它的 CI 通过才能合并。都对上了马上用 `pull_request_merge` 合并，中间不做别的事，`expectedHeadSha` 传这个提交号；然后 `unwatch_pull_request`。
4. 核实：本地切回目标分支拉取最新，重跑测试；确认目标分支上合并后的那次 CI 也通过了。
5. 向用户汇报：做成了什么、用户会看到什么变化。数字和状态都用这次核对过的。

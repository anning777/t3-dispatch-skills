# 界面文案和交互顾问

Claude 和 GPT 写界面文案都有同一个毛病：不说人话，爱堆解释性的字。Gemini 写文案最好，但会瞎编功能、乱做承诺。所以分工是：你先做出一版能用的，请 Gemini 改，最后由你对照功能核实再采纳。本机没接 Gemini 时，按第 6 步自己改。

## 1. 先做完一版

页面能打开、流程能走通，再请顾问。没做完的页面，它只能凭空猜。

## 2. 准备材料

- 这一页（或这个流程）叫什么，相关文件在哪。
- 给谁用：用户是谁，懂不懂技术。
- 要让人做成什么：用户来这一页的目的。
- 现在的文案：逐条列出位置和文字（按钮、标题、状态、提示、报错、空状态）。可以用内置浏览器打开页面，把看得到的文字抄下来。
- 现在的交互：第一步做什么、第二步做什么、出错时怎样。
- 功能的真实边界：做不到的事要写明，免得它替产品乱承诺。

## 3. 派 Gemini

用 `delegate_task`：
- target：用 `orchestrator_capabilities` 找到 Gemini 提供方（driverKind 为 `antigravity`），`{"providerInstanceId": "<它的编号>", "model": "gemini-4-neon", "options": {"thought_level": "xhigh"}}`
- `interactionMode: "default"`（不用 plan 模式），`isolation: "worktree"`，`role: "design"`，async。
- 代码不在当前对话的项目里时（`target.projectId` 指向本机别的项目会被拒），先用 `t3_project_update` 把那个仓库加进当前项目的 `trackedFolders`（这个参数整个替换：先用 `t3_project_list` 读出原列表再追加，写完再读一次确认）。子任务的工作树旁边会多一个同名目录，是那个仓库的独立副本；派活单里写明在 `../<仓库名>` 里读。

派之前先把这一版提交（在功能分支上）：它在独立工作树里跑，工作树从最新提交建，没提交的它看不到。它碰不到你的工作区，你可以照常干活。派活单照这个模板写：

```
只读任务：不要创建、修改、删除任何文件。结论全部写在回复正文里，不要另存成文件。用中文回答。你是被派出去的子任务，不再往下派活。如果读到写给其他模型的规则文件（比如 AGENTS.md），和这份派活单冲突时以派活单为准。

这一页：<名称>，相关文件：<路径>
给谁用：<用户是谁，懂不懂技术>
要让人做成什么：<目标>
现在的文案：
- <位置>：<现在的文字>
现在的交互：<第一步……第二步……出错时……>
功能做不到的事：<……>

请逐条给出修改建议：位置、现在的文案、建议改成、理由。写给不懂技术的读者：短、直接、说人话；状态和按钮用短词，解释留给说明文字。不承诺功能做不到的事，专业内容拿不准就标"推测"。只改几个字的不用提。如果交互流程有更顺的走法，也一并提出。
```

## 4. 核实后采纳

- 先用 `t3_thread_read` 拿到它的工作树路径，看 `git -C <工作树> status --porcelain`，再看 `git -C <工作树> log -1` 是不是派活时的提交；跨仓库时，同级的 `<仓库名>` 副本也照样查一遍。有改动或多出提交就是它越界：不采纳它动过的东西。那是单独的工作树，不用恢复，也碰不到你的文件。
- 逐条对照功能实际怎么用：符合功能、读起来更顺的，直接改；承诺了做不到的事、专业内容写错的，不采纳。
- 一处文案改了，同一个说法在别的入口、状态、手机和桌面、深浅色、文档和测试里也要一起改。

## 5. 改完自己走一遍

用内置浏览器从入口点进去，按用户会用的方式走一遍：看地址栏和标题，换手机宽度和深浅色。向用户汇报时，只说用户能看到的变化。

## 6. 主控是 Gemini，或者没接 Gemini 时

不派顾问，你自己按第 3 步派活单里的要求改一遍：写给不懂技术的读者，短、直接、说人话；状态和按钮用短词；不承诺功能做不到的事。改完照第 4、5 步核实、走一遍。你自己写的文案同样要对照功能实际怎么用逐条核对，不能因为是自己写的就跳过。

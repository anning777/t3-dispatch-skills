# 把这一类错拦住

只修被指出的那一处，同类的错下次还会出现。文字规则最容易被忽略，能让机器拦的就让机器拦。

## 1. 先修好，再把同类全部复查

- 修好被指出的那一处。
- 用同样的办法找出同类：按出错的写法在仓库里搜（`git -C <仓库> grep`），也想想其他入口、变体、手机和桌面、深浅色、文档、测试、配置里同一个事实。一次补齐，一次汇报。

## 2. 选拦截方式，按顺序试

1. **写成检查**：类型约束、守卫测试（测试名写清拦的是哪一类错）、脚本检查（接进 CI 或 git 钩子）。报错信息要写清该怎么改，别只说"错了"。
2. **改结构**：改接口签名、目录或封装，让错的写法根本写不出来。
3. **写成文字规则**：前两种都做不到时才用。只写做什么、不做什么，不写出过的事、日期和原因。写在哪：
   - 管你（主控）的：所有项目通用的写进你的全局规则文件，只管某个项目的写进那个项目的规则文件（CLAUDE.md、AGENTS.md 之类）；
   - 管被派出去的子任务（Codex、Gemini、DeepSeek）的：改本技能包里对应技能的派活单模板。

检查和结构改动都和修复放在同一个合并请求里。

## 3. 已有的违规

加检查时，仓库里已经存在的违规记成欠账（比如一份允许名单），检查只对名单外的报错。名单只许减少，新代码一处也不许有。

## 4. 提交说明

在提交说明末尾写一段"处理:"：哪部分用了检查或结构、拦的是什么；哪部分只能写成文字规则，以及为什么做不成检查。

## 5. 清理文字规则

- 文字规则里已经有检查守着的，只留一句，并写明是哪个检查。
- 检查已经完全守住的，删掉那段文字。

## 例子

第 1 轮审查退回："规则写着把 Codex 的改动合回主分支，会绕过审查和 CI。"
- 检查：加了 `.githooks/pre-push`，拒绝从本地推送 main，报错写清"推到功能分支、开合并请求"。
- 文字：规则改成"合进当前合并请求的功能分支"。这部分做不成检查，因为合进哪个本地分支都可能是正当操作。
- 规则里只留一句，并点名是 `.githooks/pre-push` 在守着。

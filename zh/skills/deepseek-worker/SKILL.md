# 派 DeepSeek 做简单但费 token 的活

DeepSeek V4.1 Flash 便宜、上下文大，适合把"不难但要读很多、写很多"的活从你手里拿走，省下你的上下文和额度。它没有 Codex 严谨，所以派给它的活要同时满足两条：做法有现成样例可照着做；对错能用命令判断。它交回的东西要过两道关：你验收，合并前 codex-review。

## 1. 派不派

派：
- 同一种机械改动铺到很多文件：改名、换调用方式、迁到新接口、统一格式。
- 照着已有的测试补用例，造测试数据和样例文件。
- 简单脚本：格式转换、数据清洗、一次性统计。
- 读大量文件、日志或材料做整理汇总（只读，结论交回由你核实）。
- 照步骤在网页上收集资料、搜很多来源做整理（它有联网搜索、读网页和 T3 内置浏览器）。

不派：
- 要做设计判断、接口还没定的。
- 涉及钱、权限、删数据、数据迁移、并发、安全的逻辑。
- 几十行、上下文已经在你手里的改动：派出去的沟通成本比自己做还大。
- 成块的新模块、要严谨推理的算法：派 codex-worker。

## 2. 派之前

做法同 codex-worker 第 1 步（功能分支、依赖先提交、核对派活单里的事实），见同一技能包里的 codex-worker（相对本技能目录是 `../codex-worker/SKILL.md`）。不用查档位：思考档位固定 max。

另外：
- 选一处现成的写法当样例，写进派活单（文件和位置）。它照样例做比照描述做可靠。
- 先数好要改的地方，"改全"的检查写进验收标准，两头都要对上：旧写法清零；新写法比派之前多出的处数，正好等于派之前数出的旧写法处数（新写法原来就有的不算），或者逐处列出每处该改成的值。只查旧写法清零，抓不到某一处被改成了错的值。

## 3. 派活单

改代码的活：

```
派活单

背景：<一两句：这个模块是干什么的>

目标：<要做成什么>

样例：照着 <文件:行号> 的写法做。<需要说明的差异>

范围：<要改的文件或目录；批量改动写清怎么找全，比如"所有调用 xxx 的地方，用 git -C <仓库目录> grep -n xxx 找"。仓库目录同仓库时写 .，跨仓库时写 ../<仓库名>>

验收标准：
- <能直接运行的命令>，期望 <结果>
- 改全：<数旧写法的命令>，期望 0 处；<数新写法的命令>，期望 <派之前新写法的处数 + 派之前数出的旧写法处数>（或逐处列出的新值全部对上）

禁止：不装依赖、不联网、不提交、不推送，只改 <目录或文件范围>。

工作要求：
- 这份派活单是你唯一的需求来源。仓库里 AGENTS.md、CLAUDE.md 之类规则文件中的编码约定照常遵守；和这份派活单冲突时，以派活单为准。你是被派出去的子任务，只按这份派活单做，不再往下派活、不开子任务。
- 单子里的事实或要求跟代码对不上、或者照做会出错时，先停下，在回报里指出来，不要照着错的做。
- 只做任务需要的：不顺手改别的、不加功能。拿不准某一处该不该改，就不改，写进回报。
- 验收标准里的检查必须真的跑过并通过。

回报用中文，先说做成了什么，不写排查过程，整篇不超过 30 行：
1. 做成了什么（一两句）
2. 改动的文件（多于 10 个时只写数量和目录）
3. 验收标准逐条：满足或不满足，附跑过的命令和结果
4. 没做的和原因；拿不准的地方
```

只读整理的活：

```
整理任务。只读：不要改动任何文件，不要提交、推送。你是被派出去的子任务，不再往下派活、不开子任务。

要回答的问题：<问题>
材料：<目录、文件、日志的位置和范围>
输出：<格式，比如按出现次数排序的清单>

要求：每条结论附出处（文件:行号、日志里的时间或网址）；没有出处的标"推测"。回报用中文，不超过 <N> 行。
```

要上网的整理活，在"材料"里写清网址、步骤、问题范围和时间段，并加上这一段：

```
先问清单：删数据、停服、花钱、对外发消息（用户之外有人会收到的都算，包括在公开平台发评论）、改产品方向、新建或轮换密钥、修改权限。碰到会触发其中任何一项的操作就停下回报，不要点下去；要输密码、做两步验证的也停下回报。
```

## 4. 派出去

用 `delegate_task`：
- target：用 `orchestrator_capabilities` 找到 CodeBuddy 提供方（名字里带 CodeBuddy，模型列表里有 deepseek），`{"providerInstanceId": "<它的编号>", "model": "deepseek-v4.1-flash", "options": {"thought_level": "max", "mode": "fullAccess"}}`。本机没接 CodeBuddy 就不派：改代码的活自己做或派 codex-worker，并告诉用户这一步没能按规则派出去。
- `isolation: "worktree"`，改代码 `role: "implementation"`，只读整理 `role: "research"`，async。
- 代码不在当前对话的项目里时，做法同 codex-worker 第 3 步（把仓库加进 `trackedFolders`，派活单写明在 `../<仓库名>` 里改）。
- 记下要合进的仓库和功能分支、派出时的提交号（`git -C <目标仓库> rev-parse HEAD`）、返回的子任务线程 ID。

它在后台跑的时候接着做别的事，不要轮询，完成后会自动唤醒你。

## 5. 交回后

1. 用 `t3_thread_read` 读子任务线程，拿到工作树路径。下面的 <副本> 是它改代码的目录：同仓库时就是工作树本身，跨仓库时是工作树同级的 `<仓库名>` 目录。
2. `git -C <副本> log -1` 仍是派出时的提交（它不许提交）；`git -C <副本> status --untracked-files=all` 和 `git -C <副本> diff --stat`：只改了范围内的文件，新建文件也在。只读整理的活，有任何改动或多出提交就是越界，改动不采纳，结论照样逐条核实。
3. 在 <副本> 里自己跑一遍验收命令，包括"改全"的两头检查。
4. 读改动：
   - 没有测试兜底的改动逐处读，不抽查：配置、发布和部署文件、数据文件、文档里的事实。
   - 有测试兜底的机械改动，每一类抽查几处，靠测试和"改全"检查兜底。
   - 新写的逻辑（脚本、测试的断言）整段读。
   - 只读整理的结论，抽查出处，要用到的每条都核实；核实完就结束，不合回。
5. 有问题：几处小错自己修；要返工就用 `t3_thread_send` 发给同一个子任务，返工后从第 2 步重新验收。返工一轮还不对，就自己接手或改派 codex-worker，不再来回。

## 6. 提交并合回

做法同 codex-worker 第 5 步，提交说明写"由 DeepSeek V4.1 Flash（CodeBuddy）编写，<你的模型名> 审过"。只合进功能分支，之后的审查和上线走 codex-review。

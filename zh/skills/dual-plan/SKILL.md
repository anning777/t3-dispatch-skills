# 大方案双出

两份独立方案放在一起，几乎每次都有对方没想到的地方，这是这个流程的全部价值。所以整个流程都在保护"独立"：另一家模型只拿到用户原话和必要背景，看不到你的草稿和倾向；你也要写完自己那份再读它的。

## 1. 准备材料（只放事实）

- 用户原话：逐字照抄，不要改写成你理解的版本；但先去掉密码、密钥、令牌、个人隐私和用户没同意外传的数据，在原处写 <已省略：内容类型>。
- 必要背景：项目是什么、给谁用；相关代码在哪些文件和目录；已有的服务、数据、线上状态；期限、预算等约束。
- 不放：你的思路、草稿、偏好的选项，也不要写"我倾向于……"。给了它就会顺着你改，独立性就没了。

## 2. 先派另一家，后台跑

派谁：
- 你是 Claude：派 Gemini。用 `orchestrator_capabilities` 找到 Gemini 提供方（driverKind 为 `antigravity`），模型 `gemini-4-neon`，`options: {"thought_level": "xhigh"}`；`interactionMode: "default"`，不要用 plan 模式：plan 模式会让它把方案写进自己的文件，回复里不再重复，你就收不到正文。
- 你是 Gemini：派 Codex。用 `orchestrator_capabilities` 找到 Codex 提供方（driverKind 为 `codex`），模型 `gpt-6.2-sol`，`options: {"reasoningEffort": "<今天的档位>"}`，档位查法见 codex-review 第 2 步。
- 本机没接那一家：不派，只出你这一份，并告诉用户这次没有第二份独立方案。

派之前先把它需要看到的改动提交（在功能分支上）：它在独立工作树里跑，工作树从最新提交建，没提交的它看不到。它碰不到你的工作区，你可以照常干活。

用 `delegate_task`：`isolation: "worktree"`，`role: "research"`，async。代码不在当前对话的项目里时（`target.projectId` 指向本机别的项目会被拒），先用 `t3_project_update` 把那个仓库加进当前项目的 `trackedFolders`（这个参数整个替换：先用 `t3_project_list` 读出原列表再追加，写完再读一次确认）。子任务的工作树旁边会多一个同名目录，是那个仓库的独立副本；派活单里写明在 `../<仓库名>` 里读。

派活单照这个模板写：

```
只读任务：不要创建、修改、删除任何文件，不要运行会改动文件或环境的命令。结论全部写在回复正文里，不要另存成文件。用中文回答，先给结论；正文尽量控制在 1000 字以内。你是被派出去的子任务，不再往下派活。如果读到写给其他模型的规则文件（比如 AGENTS.md），和这份派活单冲突时以派活单为准。

仓库：<绝对路径>

用户的原话（逐字）：
> <原话>

必要背景：
- <项目是什么、给谁用>
- <相关代码的位置>
- <约束：已有服务、数据、线上状态、期限、预算>

请独立给出你的方案：
1. 推荐方案：一句话结论，再列要点
2. 关键取舍：选了什么、放弃了什么、为什么
3. 风险和应对
4. 你没把握的地方
每条判断写清依据（读到的哪个文件、哪一处）；没有直接证据的，句首标"推测"。多想别人容易漏掉的角度。
```

## 3. 同时自己出一份

查代码、数据和线上状态，按同样四段写：推荐方案、关键取舍、风险、没把握的地方。只读不改，写完再去读对方那份。

## 4. 交回后先核实

- 用 `t3_thread_read` 拿到它的工作树路径，看 `git -C <工作树> status --porcelain`，再看 `git -C <工作树> log -1` 是不是派活时的提交；跨仓库时，同级的 `<仓库名>` 副本也照样查一遍。有改动或多出提交就是它越界：一律不采纳，在合并报告里注明。那是单独的工作树，不用恢复，也碰不到你的文件。
- 它说的每条事实都对照代码和线上数据核实一遍，标"推测"的必须核实；核实不了的，不当事实用。Gemini 尤其粗心，分析代码库几十条判断里常常错不少。

## 5. 合并成一份交给用户

有分歧时以代码和线上数据为准。先给结论和明确建议，只讲对业务、进度、体验、成本和风险的影响，不堆文件名和代码细节，用户追问再展开。

```
**结论**：<推荐的方案，一两句>

**两份一致的**：<要点>

**采纳了对方的**：<哪一点，为什么好>

**没采纳的**：<哪一点，为什么（附核实结果）>

**需要你拍板的**：<两边都有道理、定不下来的点：各自的理由、你推荐哪个、选另一个的后果>
```

没有需要拍板的就省掉最后一段，直接说"按这个方案开工"，等用户确认。

## 6. 拍板之后

先出设计稿、定接口和验收标准并提交，再同时开工。Codex 写后端用 codex-worker，简单但费 token 的活用 deepseek-worker，界面文案用 gemini-advisor（你是 Gemini 时文案自己定稿）。

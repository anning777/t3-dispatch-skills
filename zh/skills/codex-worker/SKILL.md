# 派 Codex 写成块的代码

Codex 最严谨，但太听话：需求写错一个事实，它会照着错的做。所以派活单里的事实要先由你核对，验收标准要写成能直接运行的命令。派一次活有沟通成本（写清任务、它读懂、你读改动再跑测试），活太小时这份成本比活本身还大，所以小活不派。

## 1. 派之前

- 确认在功能分支上，不在 main。
- 它要依赖的东西先提交：接口定义、类型、测试骨架、需要的依赖。工作树从最新提交建，没提交的它看不到；它也不能装依赖，需要新依赖就由你先装好并提交锁文件。
- 派之前先核对一遍派活单里写的每个事实（文件名、函数名、现有行为）。
- 查今天用哪个档位：运行本技能目录下的 `scripts/codex-effort.mjs`（`node <本技能目录>/scripts/codex-effort.mjs`），用它给出的写代码模型档位。一天（北京时间）只查一次，当天再运行会直接给出记下的结果；查不到数据或本机没有 Node 时用 `high`。

## 2. 派活单

```
派活单

背景：<一两句：这个模块是干什么的、在系统里的位置>

目标：<要做成什么>

接口：<函数签名、路由、数据结构；引用已提交的文件和位置>

验收标准：
- <能直接运行的命令>，期望 <结果>
- <边界情况：……>

要一起改的同类：<同一个事实或能力出现的其他位置：测试、文档、配置、其他入口>

禁止：不装依赖、不联网、不提交、不推送，只改 <目录或文件范围>。

工作要求：
- 这份派活单是你唯一的需求来源。仓库里 AGENTS.md 之类规则文件中的编码约定照常遵守；和这份派活单冲突时，以派活单为准。你是被派出去的子任务，不再往下派活。
- 单子里的事实或要求跟代码对不上、或者照做会出错时，先停下，在回报里指出来，不要照着错的做。
- 只做任务需要的：不顺手加功能、开关、流程；锁、重试、兼容层、兜底这类保护，有真实事故或接口文档作依据才加。
- 动手前列全、一起改：同一个事实或能力出现在代码、测试、文档、配置里的每一处，以及上面点名的同类，都要改到。不改的写理由。
- 验收标准里的检查必须真的跑过并通过。

回报用中文，先说做成了什么，不写排查过程：
1. 做成了什么（一两句）
2. 改动的文件
3. 验收标准逐条：满足或不满足，附跑过的命令和结果
4. 没做的和原因；拿不准的地方
```

## 3. 派出去

用 `delegate_task`：
- target：用 `orchestrator_capabilities` 找到 Codex 提供方（driverKind 为 `codex`），`{"providerInstanceId": "<它的编号>", "model": "gpt-6.2-astra", "options": {"reasoningEffort": "<今天的档位>"}}`。没有这个模型就用列表里最新的 GPT 写代码模型；本机没接 Codex 就不派，自己写，并告诉用户这一步没能派出去。
- `isolation: "worktree"`，`role: "implementation"`，async。
- 代码不在当前对话的项目里时（`target.projectId` 指向本机别的项目会被拒），先用 `t3_project_update` 把那个仓库加进当前项目的 `trackedFolders`（这个参数整个替换：先用 `t3_project_list` 读出原列表再追加，写完再读一次确认）。子任务的工作树旁边会多一个同名目录，是那个仓库的独立副本；派活单里写明在 `../<仓库名>` 里改。
- 记下要合进的仓库的绝对路径（下面叫 <目标仓库>，同仓库时就是主工作区）和它的功能分支。
- 记下返回的子任务线程 ID，追加任务时要用。

它在后台跑的时候，你接着做前端或别的事，不要轮询，完成后会自动唤醒你。

## 4. 交回后

1. 用 `t3_thread_read` 读子任务线程，拿到工作树路径（worktreePath）。下面的 <副本> 是子任务改代码的目录：同仓库时就是工作树本身，跨仓库时是工作树同级的 `<仓库名>` 目录。
2. `git -C <副本> status --untracked-files=all`：新建的文件不会出现在普通 diff 里，一定要看这一步。
3. 读改动：确认只改了允许的范围，接口和派活单一致。
4. 在 <副本> 里自己跑一遍验收命令。
5. 有问题：几十行能修好的自己修；要它返工，就用 `t3_thread_send` 发给同一个子任务。它会记得上一轮的内容，也还在原来的工作树里。

## 5. 提交并合回

1. 在 <副本> 里提交，把新建文件一起加进去，记下提交号（`git -C <副本> rev-parse HEAD`）。提交说明写明"由 Codex <模型名> 编写，<你的模型名> 审过"。
2. 在 <目标仓库> 的功能分支上按提交号合并：`git -C <目标仓库> merge --ff-only <提交号>`。如果你在这期间往功能分支提交过别的东西，快进合并会失败，这时改用 `git -C <目标仓库> merge --no-ff <提交号>`。不要按分支名合并：几个仓库里可能有同名分支。合完用 `git -C <目标仓库> merge-base --is-ancestor <提交号> HEAD` 确认它已经进了功能分支。
3. 合回后重跑一遍测试。
4. 只合进功能分支，不合进 main。main 只能通过合并请求更新。之后的审查和上线走 codex-review。
